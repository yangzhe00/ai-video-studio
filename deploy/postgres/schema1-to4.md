# PostgreSQL schema 1 → 4 发布闸门

线上 `20261030-official-04` 的 PostgreSQL 数据库曾只读观察为 schema 1。仓库当前候选 API 要求 schema 4，**本文件不是已上线记录**。既有 [schema 1→3 演练](./schema1-to3.md)仅覆盖当时的候选代码；加入灵感扩展字段后，正式发布前必须用当前源码和当前线上备份重新演练完整 1→4 路径。

## 新增结构与兼容性

`schema-v4.sql` 为 `prompt_idea_sets` 增加可空的 `parent_idea_set_id`，并用部分唯一索引限制每个原始灵感最多一个待处理、成功或待确认的扩展任务。旧记录的该字段为 `NULL`，已完成脚本仍可读。旧 `chat`／`agents` 待处理任务在迁移时转为 `unknown`，避免移除适配器后永久停留在 `pending`；不会发起新的供应商调用。schema 4 API 启动不自动迁移，schema 1／3 API 不应直接连接 schema 4 数据库。

## 发布前执行条件

1. 复核正式数据库版本、表结构、原有行数和媒体文件；备份数据库及 `API_DATA_DIR`，验证隔离恢复。
2. 在独立恢复库使用目标镜像运行 `migrate:schema`，核对 1→4 与 3→4 升级、旧记录、约束、账号权限及 API 启动；不得调用真实付费模型。
3. 更新迁移账号与运行账号对新增列／索引的权限验证。将静态网页与 API 候选代码分别验收。
4. 正式切换时停写并核对镜像 ID、备份与迁移目标，再运行迁移。迁移失败保留维护状态；迁移成功且出现新写入后，回退须先对账，不可直接恢复旧备份覆盖新数据。
5. 发布后以真实账号检查首次三条、再生成三条、刷新后的六条、选择第 4–6 条、额度与失败恢复。供应商真实生成会产生成本，需单独记录。

旧的 `deploy/postgres/schema1-to3.md` 保留为历史演练证据；其候选版本号、镜像及发布命令不能直接用于本次 schema 4 发布。
