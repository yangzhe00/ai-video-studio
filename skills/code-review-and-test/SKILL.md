# 项目代码检查与测试

默认用中文报告。先确认用户要检查的项目、分支或变更范围；如未指定，查看当前工作树与项目说明，明确本次覆盖范围。审查和测试是两种证据：代码阅读发现风险，运行结果验证可观察行为。不要把其中一种当成另一种的证明。

## 检查代码

阅读项目的 `AGENTS.md`、入口、相关实现和改动差异。沿关键用户路径检查正确性、数据与状态流、边界与错误处理、权限和敏感信息、性能及可维护性。优先报告能说明触发条件和影响的具体问题；不要把个人风格偏好写成缺陷。对于每项发现，标明严重程度、准确文件与行号、复现条件、预期与实际行为、可行修复方向。没有发现时直接说明已检查的范围，不凭空补充问题。

## 选择并运行测试

先查看项目已有命令、依赖和测试可能产生的副作用，再挑选能验证主要风险的检查：相关单元或集成测试、类型与构建、必要的端到端或手动界面操作。低影响、可逆的改动不为凑覆盖率编写镜像实现的测试。若用户只要求审查，通常不改代码；若要求修复，再在授权范围内修改并重测。运行后记录命令、退出状态和关键结果。区分新引入失败、已有失败、环境阻塞与未运行项目；不能运行时给出具体原因和下一步验证方法。

## 报告格式

1. **发现**：按严重程度排序，每条给出文件行号、原因、触发场景与影响。
2. **测试**：列出实际运行的命令和结果；界面行为需有观察证据。
3. **未验证风险**：只列可能改变结论的剩余风险。
4. **建议动作**：给出最小可执行修复或验证步骤。

保持“代码已阅读”“测试已运行”“功能已在运行中观察”三类结论分开。不要因测试通过就断言所有功能正确，也不要因某项环境失败就断言产品功能失败。
